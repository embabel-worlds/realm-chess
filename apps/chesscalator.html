Chesscalator

Play moves for either side. After each move Stockfish returns its best lines, grouped by the plan each one pursues — and on request, an explanation of how those plans differ.

Make a move, or load a position.
Scores are in pawns from White's side: +0.80 means White is better by most of a pawn. "0.34 worse" is how much a move gives up against the engine's best. Within 0.20 the engine cannot reliably tell moves apart — the choice is style, not strength. Hover a move to see it on the board; click to play it.
How it works

How it works

1. The data

Nothing on this page is stored except the plan catalogue. When you make a move, the page asks the world for BestMoves in the new position. That view pins a Position by its FEN and follows HAS_CANDIDATE to CandidateMove — a virtual type. Its rows come from the candidateLines producer, which calls the realm's own handler, chess.analysePosition. The handler runs Stockfish 19 (the lite, single-threaded WebAssembly build) under Node in the appliance's sandbox: five lines, depth 18. A position the world has not seen takes one to four seconds; a position seen in the last seven days answers from cache, which also keeps the numbers and any explanation of them in step — two searches of the same position can order close moves differently.

Each line is then read for its plan by rules, not by a model: which of the mover's pawns advance on which wing, whether a pawn strikes an enemy pawn on the mover's initiative, when and where the king castles, where both kings end up after ten plies, how many captures, and the material once exchanges settle. The first rule that matches, in a fixed order, names the plan. PlanMeaning — seeded from the realm's reference/plans.yml — says what each plan means, when it is right, what it concedes, and the rule that detects it.

2. The questions

BestMoves — "which moves are within this much of the engine's best?" Parameters: fen (the position), withinCp (default 50 centipawns; the selector above sets it), maxLines (default 5). The best move is always included.

MATCH (p:Position {fen: $fen})-[:HAS_CANDIDATE]->(c:CandidateMove)
WHERE toInteger(c.rank) = 1 OR (c.lossCp IS NOT NULL AND toInteger(c.lossCp) <= $withinCp)
OPTIONAL MATCH (m:PlanMeaning {name: c.plan})
RETURN toInteger(c.rank) AS rank, c.san AS move, c.uci AS uci, c.side AS side,
       c.scoreCp AS scoreCp, c.mate AS mate, c.whiteCp AS whiteCp, c.lossCp AS lossCp,
       c.plan AS plan, m.title AS planTitle, m.meaning AS planMeaning, c.planTags AS planTags,
       c.pvSan AS line, c.pvUci AS lineUci, toInteger(c.depth) AS depth, c.facts AS facts
ORDER BY rank
LIMIT $maxLines

The page groups the rows it gets by plan, keeping the engine's order.

ExplainPlans — "how do these plans differ?" Same fen and withinCp. It costs one model call per new position and runs only when you press the button. The model is given, per move, the rule-read facts, the plan's catalogue entry, and a verdict on its cost decided in the query — "a difference of style, not strength" within 20 centipawns, "a real, if small, concession" beyond. It is told to write from those facts only, never inventing a move or an evaluation.

MATCH (p:Position {fen: $fen})-[:HAS_CANDIDATE]->(c:CandidateMove)
WHERE toInteger(c.rank) = 1 OR (c.lossCp IS NOT NULL AND toInteger(c.lossCp) <= $withinCp)
OPTIONAL MATCH (m:PlanMeaning {name: c.plan})
WITH c, c.san + ' (' + CASE ... verdict on lossCp ... END + '): ' + c.facts
        + '. Plan "' + m.title + '" means: ' + m.meaning + ' It concedes: ' + m.concedes AS evidence
ORDER BY toInteger(c.rank)
RETURN count(c) AS movesConsidered, collect(c.san) AS moves,
       synthesize(evidence, 'Explain to a club player the choice between these candidate moves ...') AS explanation

The full query and instruction are in the realm's views/chess.yml; the realm also ships PlansInPosition (the same grouping, done in the query), PlanCatalogue and WhatPlanMeans, which this page does not call.

3. When it looks wrong

  • "The engine is thinking" for several seconds — a position the world has not seen is searched from scratch: one to four seconds, longer the first time after the appliance restarts.
  • No moves shown after a position loads — checkmate or stalemate (the status says which), or the engine did not answer; the error names the reason. A FEN the page rejects is not a legal position.
  • A plan label that seems off — the label is a reading of the engine's line by fixed rules, not a verdict on the position; read the line beneath the move. "Improve the pieces" and "Manoeuvring" mean the rules found no pawn plan to name. Report a misreading with the FEN and the line.
  • The explanation contradicts the numbers — it is written by the world's configured model from the facts shown; the numbers beside each move are the engine's and are authoritative.
  • The same position gives different moves on another day — cached lines expire after seven days, and a fresh search can order close moves differently.

4. What made this possible

  • The engine is a realm verb behind a producer, so "best moves in this position" is a query: the same MATCH (:Position {fen: $fen})-[:HAS_CANDIDATE]->(c) WHERE c.lossCp <= 50 this page runs is available to kg_query, to the assistant, and over REST — there is no chess backend to deploy.
  • The engine runs in the appliance's own sandbox as WebAssembly, and its answers are cached by the query engine per position (section 1), so this page and an assistant asking about the same position read the same lines.
  • The explanation is a synthesize() aggregation inside the query that fetched the lines (section 2), over facts computed by rules — not a separate pipeline reading raw moves.
