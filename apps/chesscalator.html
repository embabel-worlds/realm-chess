Chesscalator

What this is, and how to read it

Play moves for either side. After each move you get the engine's best lines, the position's imbalances — computed from the board, in Jeremy Silman's sense — and its opening. Ask for the plans and a model with the chess-plans skill says what each side should be trying to do.

Scores are in pawns from White's side: +0.80 means White is better by most of a pawn. "0.34 worse" is how much a move gives up against the engine's best; within 0.20 the choice is style, not strength. Green and red tags are the imbalances a move's line creates and removes. Hover a move to see it on the board; click to play it. Step through the game with the arrows under the board, the arrow keys, the browser's Back and Forward, or by clicking a move; playing a different move from an earlier position starts a new line from there.

How it works

How it works

1. The data

Nothing on this page is stored. For the position on the board the page asks the world four questions by view name; each pins a Position by its FEN and follows one relationship to a virtual type whose rows come from one of the realm's own verbs, running in the appliance's sandbox:

  • Engine lines — HAS_CANDIDATE → CandidateMove, from chess.analysePosition: Stockfish 19 (lite, single-threaded WebAssembly) under Node, five lines at depth 18. Each line also carries the imbalances it creates and removes once its exchanges settle. Cached for seven days per position — a search is not repeatable, and the cache keeps the numbers steady.
  • Imbalances — HAS_IMBALANCES → PositionImbalances, from chess.positionImbalances: computed from the board, never judged. Material, bishop pair and good/bad bishops, doubled, isolated, backward, passed and hanging pawns, majorities, locked chains and the wing they point to, space, files, outposts, development, king safety. Also which named opening's pawn structure this is, matched on the pawns alone against the opening book.
  • Opening — IN_OPENING → Opening: the Lichess opening book (3,815 named lines, CC0). A game played from the start is looked up as a GameLine — its moves — and keeps the deepest name it passed through (chess.openingOfGameLine), so twenty moves into the Exchange Ruy Lopez it is still called that. A position loaded from a FEN has no moves behind it and is looked up by position (chess.openingLookup).
  • Opening theory — GameLine HAS_THEORY → OpeningTheory, from chess.theoryOfGameLine: the deepest page of the Chess Opening Theory wikibook the game's moves reach, read through the Wikibooks API, shown as an excerpt with its authors and licence (CC BY-SA 4.0). Cached for a week.
  • Tactics — also computed from the board and listed first: check, mate in one, a mate threat, a piece attacked and not defended, a piece attacked by a cheaper one. These are facts, not verdicts: whether taking a loose piece works is the engine's call. Material is counted once an exchange under way is finished, so straight after 4.Bxc6 the sides are level, not "White three points up".
  • Plans — HAS_PLAN → Plan, from chess.explainPlans, only when you press Show the plans: the three above go to gateway.ai.complete with the chess-plans skill attached — with the opening theory too, for a game played here — and the model names up to three plans for each side, citing the imbalances it uses by number. The facts are computed; the plans are its judgement. Cached for seven days.

2. The questions

BestMoves — fen, withinCp (default 50; the selector sets it), maxLines (default 5). The best move is always included.

MATCH (p:Position {fen: $fen})-[:HAS_CANDIDATE]->(c:CandidateMove)
WHERE toInteger(c.rank) = 1 OR (c.lossCp IS NOT NULL AND toInteger(c.lossCp) <= $withinCp)
RETURN toInteger(c.rank) AS rank, c.san AS move, c.uci AS uci, c.side AS side,
       c.scoreCp AS scoreCp, c.mate AS mate, c.whiteCp AS whiteCp, c.lossCp AS lossCp,
       c.pvSan AS line, c.pvUci AS lineUci, toInteger(c.depth) AS depth,
       c.creates AS creates, c.removes AS removes
ORDER BY rank
LIMIT $maxLines

ImbalancesOf — fen.

MATCH (p:Position {fen: $fen})-[:HAS_IMBALANCES]->(i:PositionImbalances)
RETURN i.sideToMove AS sideToMove, i.phase AS phase, i.facts AS facts, i.structure AS structure, ...

OpeningOfLine — moves (SAN from the start), for a game played on this board.

MATCH (g:GameLine {moves: $moves})-[:IN_OPENING]->(o:Opening)
RETURN o.eco AS eco, o.name AS name, o.pgn AS bookMoves,
       toInteger(o.namedAtPly) AS namedAtPly, toInteger(o.pliesPast) AS pliesPast

TheoryOfLine — moves.

MATCH (g:GameLine {moves: $moves})-[:HAS_THEORY]->(t:OpeningTheory)
RETURN t.title AS page, t.url AS url, t.theory AS theory, toInteger(t.pliesCovered) AS pliesCovered,
       toInteger(t.pliesPast) AS pliesPast, t.licence AS licence

OpeningOf — fen, for a position loaded from a FEN.

MATCH (p:Position {fen: $fen})-[:IN_OPENING]->(o:Opening)
RETURN o.eco AS eco, o.name AS name, o.pgn AS moves

PlansInLine — moves, level — for a game played from the start, so the model is told the line's opening name; PlansInPosition — fen — otherwise. The same query shape from a GameLine or a Position, filtered WHERE pl.level = $level: the level is pushed down to the verb, so a beginner, an intermediate player and an expert each get plans written for them, each judged and cached separately. One engine search and one model call per new position and level.

MATCH (p:Position {fen: $fen})-[:HAS_PLAN]->(pl:Plan)
RETURN pl.side AS side, toInteger(pl.priority) AS priority, pl.name AS plan, pl.idea AS idea,
       pl.moves AS moves, pl.imbalances AS imbalances, pl.engineEvidence AS engineEvidence,
       pl.summary AS summary, pl.structure AS structure, pl.opening AS opening
ORDER BY side DESC, priority

The same four views answer kg_query, the assistant, and REST; the full definitions are in the realm's views/chess.yml, and the plan knowledge is its skills/chess-plans/SKILL.md.

3. When it looks wrong

  • "The engine is thinking" for several seconds — a new position is searched from scratch, one to four seconds; longer the first time after the appliance restarts.
  • The plans take half a minute — an engine search and a model call. The second time is instant.
  • No opening name — for a game played here, the book never named any position along it; for a loaded FEN, the position itself is deeper than the book. Either way the imbalances say which book line's pawn structure it has, when one is close.
  • Back and Forward step through the game, as do the arrows under the board and the arrow keys; the address carries the game, so a reload or a shared link opens the same position.
  • A plan that seems wrong — plans are a model's judgement, and the battery of test positions shipped with the realm shows how often it matches theory. The imbalances and the engine's numbers are computed and authoritative; a plan that contradicts them is the plan's fault. Report it with the FEN.
  • No opening theory — the wikibook has no page along this line, or the position was loaded from a FEN and has no moves behind it.
  • An imbalance that is wrong — that is a bug in the realm's computation; report it with the FEN.
  • The plans fail to load — they need an appliance whose gateway.ai.complete accepts skills; the rest of the page works without it.

4. What made this possible

  • The engine, the imbalances and the opening book are realm verbs behind producers, so "the best moves in this position" or "who has the bishop pair" is a query — the same MATCH (:Position {fen: $fen}) this page runs is open to kg_query, the assistant and REST. There is no chess backend to deploy.
  • The plan knowledge is a skill, not code: the model gets it through the framework's Skills, the same way chat does, so improving the plans means editing SKILL.md.
